# The Routing module is a separate program in front of unmodified public cores

The closed part of the hosted service, the Routing module, is its own program. It imports no package of the public repo, runs the public core's released image unmodified as a pool of identical, stateless cores, and talks to them over HTTP only, handing each request or run the Context of one Family. Whatever both sides must agree on (the Context's format, the operations that can be triggered from outside) is taken from the core's public documentation, not from its source ([#90](https://github.com/artkoenig/family-agenda-cloud/issues/90)).

The reason is the licence. The public repo is AGPLv3 with contributions under the DCO and no CLA (public ADR-0006). Once someone else has contributed, the owner cannot relicense the core, and a program that imports its packages into one process is very likely a work based on it and bound by the AGPL as a whole (`docs/research/agpl-contribution-options.md`, F3). A separate program that talks to the core over a network protocol can stay closed.

This supersedes the in-process plan of `docs/skalierung-refactorings.md`: its Phase 2, where the closed code imports the public packages and runs many Instances with an LRU cache in one process, and, for the public repo, its items 1.1 (composition root as a library), 1.4 (HTTP app without its own server) and 1.7 (publishing the packages). The core's side is [artkoenig/family-agenda#362](https://github.com/artkoenig/family-agenda/issues/362) instead.

## Consequences

- Memory grows with load, not with the number of Families: scaling is starting one more core, which needs to know nothing about Families.
- The core must accept a Context per request, serve below a path prefix and offer its due work, purge and password reset as operations triggered from outside. The Routing module is built and tested against a stand-in core that mirrors the core's documentation, and walked through against the core's image.
- A new core version reaches the Families through the cores alone ([#119](https://github.com/artkoenig/family-agenda-cloud/issues/119), [artkoenig/family-agenda#405](https://github.com/artkoenig/family-agenda/issues/405)). A core prepares a Family's database when it first opens it; the Routing module prepares none, has no roll-out, and keeps no record of which core version a Family was prepared for or which one the pool runs. While cores of two releases run side by side, one of the older release refuses a Family the newer one has migrated, and one still preparing a Family says so; the Router, the Scheduler and Provisioning then try the next core of the pool, each core at most once, and fail with what each core answered when all refuse. A refusal is the core's word that it changed nothing, so even a request with a body or a password reset may go to another core after it. Going back to an older core version is a restore, not a deploy.
- The pool is one service with replicas, and the Routing module is told its name, not a list of cores ([#120](https://github.com/artkoenig/family-agenda-cloud/issues/120)). It resolves the name at each call, spreads its calls over every address the name stands for then, and goes on to the next when one cannot be connected to. Scaling the pool is one number changed on the Cube and needs no restart of the Routing module. The price is a name lookup per call, which has no time limit of its own, so a name service that is slow slows every request; and that the Routing module depends on the Cube's name service answering with every replica, as Docker's does for a name the replicas of a Compose service share on one network.
- The Routing module is on every web request and every scheduled run, and the Context carries a family key and a database password across the internal network, so it is encrypted. A core answers browser requests on one port, each with a Context, and its triggered operations on another, behind a bearer token. Only the Routing module holds the Context key and the token. The network does not keep other callers out: the plugins and their Egress Proxies share networks with the cores and can reach both ports, so the key and the token are what guard them.
- The Router and the Scheduler read a Family's status once, at arrival, and take no lock. A suspend or delete therefore does not stop a request or run already past that read: it is still handed its Context, a core that has the Family open keeps it open until it was idle for five minutes, and the plugins' Tickets open the Family's hosts until they expire. A deleted Family's database is dropped only once no core holds it open. This is accepted: the window is bounded, it only ever reaches the Family's own data and hosts, and closing it would need a lock on every request or a call into every core on each status change. `spec/tenantIsolation.qnt` checks that no request, run or Ticket reaches another Family and that none arriving while its Family is not active gets a Context, and shows the window ([#149](https://github.com/artkoenig/family-agenda-cloud/issues/149)).
- All Families share one browser origin, `app.family-agenda.cloud`, so a script that escapes one Family's pages could reach another's. A Content Security Policy is a gate before registration opens.
