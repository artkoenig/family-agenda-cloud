## Resolution

Reframed: hosted registration (landing page with OIDC login, billing) triggers provisioning and creation of the Instance's Admin, so setup is automated by the embedder through the library, not via CLI or web setup. The ticket title's "CLI" parts are dropped.

- **Programmatic setup API** on `application`, usable without HTTP: `createFirstAdmin({ email, password? })` (password optional, i.e. a passwordless Admin) and a function to configure the Identity Provider (same validation as the Admin area; client secret via the `SecretStore`).
- **No new CLI commands** (`create-admin`, `set-llm-endpoint` dropped). The CLI stays as is (`reset-admin-password` only). No setup token. `/setup` stays open by default, unchanged for self-hosters.
- **LLM endpoint:** no new mechanism. Hosted extraction comes through the injected `Extractor`; self-hosters keep the Admin area.
- **Identity Provider setting** "Create new Admins on sign-in" (default on, as today). The embedder switches it off; then only the pre-created Admin can sign in, linked by verified email. The required group becomes optional (empty = no check), because a shared Identity Provider keeps no group per Family. Small amendment to ADR-0017 (public repo, status proposed); also useful for self-hosters with a closed circle of Admins.
- **Email verification:** with OIDC login an Admin is linked by email only if the provider reports `email_verified=true`; missing or false means the sign-in is rejected. To check during implementation how ADR-0017's code handles this today.
- **Out of this map (Phase 2):** registering the per-Family redirect URI (`<public base URL>/sso/callback`) at the landing page's Identity Provider (wildcard or dynamic).
