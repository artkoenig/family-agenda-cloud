## Resolution

- **Lazy migration on open:** each Family has its own DB, so `bootApplication` keeps migrating (always) when the Instance is opened. The advisory lock already serialises concurrent opens; the hosting pool should open one Instance per Family at a time (single-flight). The scheduler also opens a Family before `runDueWork`, so stale DBs are brought up to date on next use. No rollout loop over all DBs, no `readMigrationStatus`, no `migrate: "never"` option, no `migrateDatabase(url)`.
- **Stable API (SemVer):** `runMigrations`, `connectPostgres`/`PostgresConnection`, and the error classes `OldMigrationHistoryError` and `NewerMigrationHistoryError` (`instanceof` is the contract). A failing migration affects only that Family.
- **Mixed versions:** during a rolling deploy old and new processes coexist; `NewerMigrationHistoryError` protects old processes from an already migrated DB, and the pool must treat it as "reject or restart this Family's process". Migrations are additive (expand/contract); removing or renaming something old code needs is Major-only. Rollback means restoring a backup, no down-migrations.
- **Note for migration authors:** long migrations run in the first open after a release.
- **1.7:** the `drizzle/` migration files are a static asset to package (see fog).
