## Question

How does the **public image** serve many Families from stateless, horizontally scalable `api` and `worker` containers, each Family with its own database, while self-hosting runs the same image with one container of each kind and one Family?

## Settled by the maintainer (2026-11-07)

- **One image for both.** The cloud runs the public image (`ghcr.io/artkoenig/family-agenda`), not a derived private image. Containers are stateless and run in parallel; only the database is bound to a Family. Self-hosting: one `api`, one `worker`, one Family.
- **Which Family a request belongs to:**
  - signed in (hosted): from the OIDC token (a Family claim), verified server-side; never from a plain cookie or header.
  - Agendas, their ICS feed and photos (no sign-in): from the **Agenda link**, which identifies Family and Agenda and cannot be guessed (signed token or random secret; to decide here). It replaces today's bare UUID.
  - worker: no request; it goes through the Families that have work due.
- **Agenda links never expire and have no version or rotation.** An Admin revokes a link by deleting the Agenda. This amends ADR-0005 (which asked for rotatable Agenda Links).
- The private repo shrinks to landing page, registration, provisioning (writing the Family claim at the Identity Provider), billing, operations.

## To decide here

- Family register: where (control database vs config), what it holds (database, key reference), one entry from `DATABASE_URL` when self-hosted.
- Agenda link format: signed token (key per Family) vs random secret stored hashed; length (QR codes), leakage in logs/history/Referer.
- Worker across containers: how Families are picked (due index), and a database lock so two workers never poll the same Family/Source at once (today only the in-memory `polling ??=` guards it); in-memory values (`lastPurgeAt`, Recovery Kit `confirmed`) move to the database or are made harmless.
- Stateless containers: blobs to S3, master key per Family from KMS, tessdata in the image; file adapters stay for self-hosting.
- A person in several Families (e.g. separated parents): list claim and a Family switcher, or one Family per person.
- Instance lifecycle in a shared process: open/close per request or pooled (connections per database).

## Resolution

**Addressing**
- One address for all Families (`app.<domain>`), no subdomains. Admin paths stay `/admin/...` everywhere; the Family of a signed-in request comes from the session. Agendas carry the Family in the path (format: "Decide Agenda link format", #21).
- **Session cookie** `<Family id>.<session token>`; the session row stays in the Family database (token hashed, as today). A changed Family id finds no session in the other database, so no signature is needed. Self-hosted: no Family id, cookie as today.

**Sign-in when hosted**
- The operator configures Identity Providers through the image's configuration (env), including third-party ones such as Google. The Family database's `identity_provider` row and its Admin page are unused when hosted; no password sign-in when hosted. Self-hosted unchanged.
- **Identity → Family** mapping lives in the register: (issuer, subject / verified email) → Family. Provisioning writes the first Admin; creating an Admin in the Admin area also writes the mapping. No broker IdP.
- A person in several Families: **out of scope**; one Family per person.

**Family register**
- A port in the public code. Self-hosted: exactly one Family from `DATABASE_URL`, no table. Hosted: a control database (`CONTROL_DATABASE_URL`, switches the hosted mode on) with Family id → database, wrapped Family key, status, due time. Family ids are random, not speaking. Provisioning (private repo) creates Families.

**Workers**
- Due index in the control database: a worker claims due Families with `FOR UPDATE SKIP LOCKED` and a lease, runs `dueWork.run()`, writes back `nextDueAt()`. An advisory lock per Family database as second guard (the only guard self-hosted). New work (e.g. a Source added) sets the Family due now; this settles "waking the worker".
- `dueWork` is polling and extraction only; **retention moves to cleanup** (changes "Decide worker as due-work functions (1.3)").

**Cleanup**
- Own container kind `cleanup` (image start command), running e.g. daily over all Families in the register: (1) retention: messages older than X or no longer needed, (2) secret sweep, (3) final deletion of Families whose closing is due. Self-hosted: the same code as a daily timer inside the worker container, no extra container.
- **X** is set by the operator in the image configuration (default 180 days, today's `messageRetentionDays`), not per Family, and published in the privacy policy (GDPR art. 5 (1)(e), art. 13 (2)(a)). No `lastPurgeAt` per Family.
- **Close Family** (hosted only): an Admin requests it with confirmation; a Backup download is offered first; the Family is locked at once (no sign-in, Agenda links invalid, no polling); after a grace period (e.g. 14 days) cleanup deletes the Family database, its blob prefix, its key, the register entry and its identity mappings. Grace period stated in the privacy policy.
- Operator backups drop closed Families as they expire (e.g. 30 days, stated in the privacy policy); the backup system is private-repo work.

**Stateless containers**
- S3-compatible `BlobStore` adapter with a prefix per Family; files stay the default.
- Each Family's master key is stored in the register, wrapped by an operator key (key encryption key) the image reads from env or a Docker secret; a vendor KMS can come later as another adapter. OCR models: "Decide OCR models in hosted operation" (#22).
- The Recovery Kit `confirmed` cache is harmless (only changes from no to yes); new in-memory state is barred by the 1.9 lint rule.

**Open Instances per container**
- LRU of open Instances (connection + wired use cases), each with a small pool (1–2 connections), closed after an idle time (e.g. 5 min); maximum count and idle time configurable; concurrent requests for one Family open it once (single-flight). Self-hosted: the one Instance stays open.

**Comment by artkoenig, 2026-11-07T14:39:14Z**

## Resolved: grace period when closing a Family

- After closing, the Family is locked at once: no sign-in, Agenda links stop working, workers skip it.
- The grace period stays, with only one purpose: on request, the Operator can undo the closing. The Family cannot undo it itself.
- Length: Operator setting, default **7 days**.
- After the grace period, cleanup deletes the Family for good: its database, its blobs, its wrapped key and its register entries.
- Before locking, the closing dialog offers the Backup download (as in the Backup decision).
