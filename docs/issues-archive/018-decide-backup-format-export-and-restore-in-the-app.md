## Question

What is the Backup the app itself creates and restores, and how does restoring re-key secrets? Public-repo feature (own ADR), the basis of the "export, no lock-in" principle (#5) in both directions (self-hosting ↔ hosted).

## Settled by the maintainer

- **Only Backups made by the app.** No import of the manual `pg_dump` + volume backups from `docs/upgrading.md`. Existing Instances get a way to create an app Backup before relying on it.
- **Only a signed-in Admin may restore.** No restore path without a signed-in Admin (not in onboarding either; see the onboarding ticket).
- **Restore is possible later too**, from a Backup area in the Admin area, not only during onboarding.

## Facts from the code (main @ 83a960d)

- No backup/export/restore exists in the app. `docs/upgrading.md` holds unrehearsed Docker commands.
- The Recovery Kit text already promises "Backups are encrypted with a key derived from it" (`apps/api/src/http/i18n/en.ts:205`); not implemented.
- `EnvelopeSecretStore` keeps secrets **in the Family database**, wrapped with the master key (`apps/api/src/composition-root.ts`, `resolveStores`). A Backup therefore carries secrets wrapped with the *old* master key.
- `OldMigrationHistoryError` / `NewerMigrationHistoryError` already exist.

## Proposal to grill

- **Contents:** logical export of the Family database, the blobs, the migration version; secrets as stored (wrapped with the source Instance's master key). Encrypted with a key derived from the Recovery Kit (ADR-0006).
- **Restore:** upload + Recovery Kit → unwrap secrets with the kit, re-wrap with **this** Instance's master key (file when self-hosted, per-Family KMS key when hosted). Older Backup → migrate after import; newer → refuse.
- **Not included:** Matrix sessions (Synapse DB, `matrix-data`). Matrix Sources come back Failing and need "Fix"; on a hosted Instance they are not restored at all (#5: Matrix never hosted).
- **LLM endpoint:** restored when self-hosted; discarded (with its secret) when the endpoint is set by the embedder (see the onboarding ticket).

## Open

- Restore replaces all Family data, including Admins. What happens to the Admin who is signed in and restoring? Proposal: the restoring Admin is kept (merged with the Backup's Admin of the same verified email, else added), so a hosted Family whose Admin was created by provisioning (#7) cannot lock itself out; their session ends and they sign in again.
- Restoring later over a non-empty Instance: confirmation step, and a Backup of the current state first?
- Size limits and streaming for large blob sets; where hosted Backups are stored (out of this map).
- Does `Recovery Kit` stay required on a hosted Instance? Proposal: yes, it is the way back to self-hosting (answers #17).

## Decision (maintainer, 2026-11-07)

**The restoring Admin is kept.** A restore replaces all Family data, including the Backup's Admins, except the Admin who is signed in and restoring:

- If the Backup has an Admin with the same verified email, the two are merged (the restoring Admin's sign-in methods, password and/or Identity Provider subject, are kept).
- Otherwise the restoring Admin is added to the restored Admins.
- Their session ends with the restore; they sign in again.

Reason: a hosted Family whose Admin was created by provisioning (#7) must not lock itself out by restoring a self-hosted Backup.

Still open in this ticket: confirmation and a Backup of the current state before restoring over a non-empty Instance; size limits/streaming.

## Resolution (maintainer, 2026-11-07)

Builds on the earlier decision in this ticket (restoring Admin kept). Public-repo feature; an ADR is drafted when the work is handed off.

**Key: the Family takes over the Backup's master key.** Restore needs the Recovery Kit of the source; the Family adopts that master key (hosted: wrapped via `KeyWrapper`). Data, blobs, credentials, `external_id` HMACs and Agenda-link tokens stay valid as stored; nothing is re-keyed. The Family's previous Recovery Kit becomes invalid, and the UI says so. This is not a rotation: the whole Family, key included, is replaced. (Re-keying everything under the target key was rejected: a run over all columns and blobs that breaks when interrupted.)

**Format:** an image of all Family database tables as stored (content stays ciphertext), all blobs, and the migration version, written as one stream and encrypted as a whole with a backup key derived (HKDF) from the master key (AES-256-GCM in chunks), so the plain structure (times, statuses) is protected too. Older Backup → loaded at its version, then migrated; newer → refused (`NewerMigrationHistoryError`). No separate domain-level export format.

**Not included:** sessions; Matrix data (Matrix Sources come back Failing and need "Fix"; not restored at all when hosted); the LLM endpoint, **neither self-hosted nor hosted**. Messages beyond the retention period are removed by the cleanup worker after the restore.

**LLM endpoint on restore:** the target keeps its own endpoint. Without one (fresh Instance), the Admin sets it as in onboarding; until then Messages wait unprocessed.

**Restore over a non-empty Instance:** upload + Recovery Kit → check (decryptable, version) → summary (date, counts of Sources, Events, Family Members) → confirm by typing a word → apply: database in one transaction; blobs written first, old ones removed only after commit. An interruption leaves the old state. No "download current state first" step, no server-side copy.

**Size:** export and import stream, never all in memory. No limit self-hosted; hosted, the operator configures a maximum upload size.

**Closing a Family:** no sign-in after closing, so no download during the grace period. The closing dialog offers the Backup download as a step before the Family is locked; the Admin may skip it on purpose.

**Scope:** manual download only; nothing stored on the server. Scheduled Backups to own storage → out of scope for this map.

**Recovery Kit stays required hosted** for Backups: without it a Backup cannot be restored; it is the way back to self-hosting.

**Glossary (public repo, at hand-off):** "Recovery Kit" changes from "without it, a backup cannot restore Source credentials" to "without it, a Backup cannot be restored"; add **Backup**: the encrypted file an Admin downloads from the app, which restores the whole Family in any Instance together with its Recovery Kit.
